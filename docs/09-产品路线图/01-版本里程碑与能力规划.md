# 产品版本里程碑与能力规划

阅读位置：`09.01` · 面向集群管理员和项目维护者 · [返回文档导航](../00-文档导航.md)。

当前正式版本为 **0.3.0**。0.1.0～0.3.0 已发布；0.4.0 正在调整为独立监控中心与推送式 Agent 架构，尚未达到候选发布条件；0.5.0 及后续版本处于规划阶段。0.4.0 尚未创建 tag 或 Release。版本号和顺序不代表发布日期承诺；各阶段以已有能力为基础，交付可独立使用的结果。

Atlas KubeKit 的目标是通过清晰的脚本选项，帮助管理员完成 Kubernetes 集群部署及持续运维。路线图围绕集群可用、可观察、可恢复、可升级、安全管理和稳定交付展开。1.0.0 的“全功能”指本文和发布时支持矩阵共同定义的生产基线，不表示覆盖所有云平台、业务数据库或跨地域灾备方案。

## 0.1.0：集群部署基础（已发布）

**发布日期**：2026-10-02 · **标签**：`v0.1.0`

提供 Ubuntu Server 24.04 amd64 节点准备、重启续跑和集中式 Kubernetes 集群编排；通过插件菜单安装 14 项可选组件，并按节点角色进行日常检查。该版本建立了从主机准备到基础集群可用的操作入口。

## 0.2.0：集群审计与 LB 管理（已发布）

**发布日期**：2026-10-22 · **标签**：`v0.2.0`

增加 HAProxy/Keepalived 运维入口、业务 VIP 与转发规则管理，提供旧集群审计和基线修复流程；扩展多语言目录、存储检测、统一下载源和插件版本匹配，插件菜单扩充至 16 项。LB 管理仍按该版本声明的试用范围使用。

## 0.3.0：持续运维与离线交付（已发布）

**发布日期**：2026-11-10 · **标签**：`v0.3.0`

增加持续运维入口，提供统一配置与变更预览、安全交接、控制面加密备份与隔离恢复准备、worker 生命周期和补丁升级、报告诊断及锁定离线物料。卷和应用数据恢复、生产原位 etcd 恢复及控制面成员变更仍有独立边界。

已发布版本的完整变化和兼容性说明见[变更记录](../../CHANGELOG.md)。

## 0.4.0：独立监控中心、监控与告警（开发中）

**用户收益**：管理员能知道集群和关键业务哪些风险受到监控、哪些仍有盲区，并在故障或风险出现和恢复时收到通知。

**部署架构**：专用监控中心统一运行 Prometheus、规则、Alertmanager、Grafana、Loki 和通知服务；业务集群只运行 Prometheus Agent 与 Alloy，通过 HTTPS 推送指标和日志。每个业务集群使用唯一 `cluster` 标签。旧的单集群全栈 E2E 只能作为原部署模式的证据，不能替代中心和 Agent 的跨集群验收。

**交付范围**：

- 基于现有监控栈，接入控制面和 etcd、节点、网络与 DNS、工作负载、存储、LB、证书及监控自身等适用对象；将业务入口与外部依赖按实际环境登记。备份新鲜度、校验和恢复结果的周期监控归入 0.5.0；0.4.0 覆盖报告须把在用备份风险显示为缺口。具体首批风险及数据源以[风险覆盖矩阵](../07-监控与预警/02-生产监控指标与告警覆盖矩阵.md)细化。
- 提供可配置的规则、阈值、时间窗口、等级、对象范围和恢复条件，支持预览、校验及明确的覆盖/缺失状态。
- 支持企业微信、钉钉、飞书群机器人和邮件通知，包含故障与恢复消息、渠道测试、失败状态和受保护的凭据引用。
- 将告警关联日志纳入 03 首装向导和一键部署：按 QA 收集日志范围、持久化/保留和通知配置，接入受控采集器与 Loki，并以有界、脱敏的中文日志片段丰富邮件和机器人告警；只有显式配置且校验过访问保护的 HTTPS Grafana Explore 入口时才附链接，否则不附链接、直接附日志摘要。
- 提供告警分组、抑制、静默和责任组路由；记录未覆盖、数据缺失及渠道不可用，避免把未采集当作健康。
- 建立集群外可独立通知的观察和心跳路径，并说明观察者的故障域；监控栈本身的采集、规则和通知状态可见。

**完成条件**：明确首批适用风险及不适用原因；管理员能通过脚本一键配置、检查和更新指标、规则、日志诊断及通知；告警关联日志范围受控、敏感内容有保护、消息长度有上限；有无外部 HTTPS 入口两条通知路径均经过验证；每个声明支持的通知渠道在授权环境中验证故障与恢复送达；至少验证一个中心和两个 Agent 集群的指标/日志接收、集群身份隔离、告警触发/恢复、断连与回补/数据缺口、中心故障外部观察及重复执行清理；覆盖缺口、通知失败和集群内监控不可用时的外部观察均可识别。环境阈值、业务成功条件与通知责任人由用户配置，不给所有生产环境套用同一数值。

**发布边界**：业务 SLO 和合成业务交易、数据库/缓存/消息队列专属指标、备份新鲜度及恢复结果、Gateway/Ingress 控制器专属指标均不得因为未配置而显示为健康。集群负责人需在覆盖档案中登记适用性、指标/目标和验收人；0.5.0 承接备份与恢复观测，入口控制器能力按后续里程碑规划。公网 Grafana 域名、TLS、认证和手机外网可达性由部署环境 QA 验收；未配置有效公网 HTTPS Explore URL 时通知仍提供有界日志摘要且不含链接。

功能目标和规则原则以[生产监控与预警功能定义](../07-监控与预警/01-生产监控与预警功能定义.md)为准；本文仅定义版本归属与交付结果。可按纵向切片分批开发，但 0.4.0 正式发布的范围和未覆盖项目必须明确。

## 0.5.0：数据保护与恢复（规划中）

**用户收益**：管理员能按计划保护控制面和已登记的业务数据，知道备份在哪里、是否可用以及如何恢复。

**计划范围**：配置周期、保留期和受保护目标；支持远端或异地备份位置及密钥引用；查看备份状态与告警；提供控制面恢复操作和隔离演练。明确 PVC 与数据库的支持方式，为代表性组件提供可执行的备份和恢复路径，其他组件以用户提供的工具或适配器接入。

**完成条件**：在声明支持的目标存储和代表性工作负载上完成定时备份、异地保存、校验、隔离恢复和应用读写检查；验证备份失败、过期、不可达及错误凭据的提示和告警。明确 RPO/RTO 为环境配置和演练结果，不能凭备份文件存在推断恢复成功。

## 0.6.0：集群生命周期与升级（规划中）

**用户收益**：管理员可以在了解影响和前提后扩缩容、维护节点、升级集群，并在失败后继续处理。

**计划范围**：完善 worker 加入、退出和替换；规划并支持声明范围内的控制面成员操作；建立 Kubernetes 及相关组件的受控升级路径，包括支持的跨 minor 升级组合、兼容检查、备份前提、逐节点执行和失败恢复。具体支持的版本与拓扑在该阶段确定。

**完成条件**：在支持矩阵列出的典型拓扑上验证节点和控制面操作、版本升级、中断继续、PDB/存储/etcd 前提及操作后的业务访问；不支持的版本组合在执行前明确拒绝并给出处理建议。升级回滚和数据恢复各自说明适用条件。

## 0.7.0：LB 与业务入口（规划中）

**用户收益**：通过脚本查看 LB 状态并管理业务入口，减少手工修改 HAProxy 和 Keepalived 配置。

**计划范围**：完成自有 LB 节点、业务 VIP 和转发规则管理；完善配置预览、校验、备份、逐节点发布、失败恢复、状态和健康检查；明确 API 与业务 VIP 的故障关联、TCP/HTTP 路由、长连接、Gateway/Ingress、DNS、TLS 和外部网络配置的责任边界。具体支持的路由和证书管理方式在该阶段确定。

**完成条件**：支持矩阵内的双 LB 环境完成规则增删改、重跑、部分失败恢复、VIP 切换及业务访问检查；清晰展示不支持的规则和外部 LB 能力。长连接的断线与重连行为需有明确说明。

## 0.8.0：安全与权限（规划中）

**用户收益**：部署后的管理权限和敏感凭据有清晰归属，日常运维不必长期依赖部署阶段的临时授权。

**计划范围**：梳理部署、日常运维、只读巡检等身份及其权限；完善部署收尾、SSH 主机身份核对、授权收回和恢复路径；统一监控渠道、备份目标和企业仓库的凭据引用、轮换及敏感信息保护；记录操作结果。

**完成条件**：在声明支持的身份与权限模型下完成部署、交接、日常操作、凭据轮换及授权失败处理；确认临时授权可清理、保留管理通道可用，敏感内容不进入普通输出和报告。无法自动完成的外部身份管理步骤提供明确指引。

## 0.9.0：兼容性与稳定契约（规划中）

**用户收益**：部署前知道支持的环境；升级脚本或集群时知道兼容性、迁移步骤和可能影响。

**计划范围**：发布支持矩阵，覆盖 Ubuntu、CPU 架构、Kubernetes/Cilium 版本、节点拓扑、网络和存储前提；冻结 1.0 的脚本入口、参数、配置格式、退出码与数据迁移规则；提供从已支持旧版本升级、回退及配置迁移的指南；完善功能、组件、架构、安装和故障处理文档。

**完成条件**：每个承诺支持的组合有明确检查方式和对应验证；从指定旧版本升级到候选版本的路径可执行；不兼容变更、已知限制和人工步骤可查询。未验证的组合不标记为已支持。

## 1.0.0：声明范围内的完整生产基线（规划中）

在 0.4.0～0.9.0 的发布范围完成并合并后，生成候选版本并按 0.9.0 支持矩阵验证。发布前至少满足：

1. 新部署、既有集群升级、节点/LB 管理和脚本重复执行均有清楚的操作及异常处理路径。
2. 必需监控覆盖、告警规则、四类通知渠道及独立观察路径达到 0.4.0 声明的范围；未覆盖项可见。
3. 控制面与声明支持的 PVC/应用数据备份可按计划保护，并在隔离环境恢复、核对业务读写；明确恢复对象和环境。
4. 典型支持拓扑完成控制面、worker、LB、存储和监控故障场景的恢复检查；检查覆盖不等同于所有环境都能零中断。
5. 部署和运维权限、凭据管理、授权收尾、兼容矩阵、升级迁移及用户手册完成，所有发布阻断问题已解决或明确退出支持范围。
6. 候选版本的源码、制品、配置和验证环境可对应；完成用户可复查的功能、限制与升级说明后，再按项目版本规范发布正式版。

跨地域灾备编排、任意数据库自动恢复、任意云厂商 LB API 和所有硬件设施并非自动纳入 1.0.0；如后续纳入，需在对应版本明确支持对象、配置方式和完成条件。

## 依赖与推进原则

- 先建设 0.4.0 可用的采集、规则与通知路径，0.5.0 再把备份状态和恢复结果接入监控；各能力以实际环境配置为准。
- 0.5.0 提供恢复基础，0.6.0 的升级操作使用明确的保护前提；0.7.0 的入口故障告警复用 0.4.0 机制。
- 0.8.0 将已有渠道和运维功能纳入一致的凭据与权限管理；0.9.0 汇总各版本实际支持范围，而非预先将目标写为已支持。
- 每个阶段完成后更新用户功能说明和变更记录。具体需求、技术方案、参数、测试范围和实现任务按该阶段细化；不以规划表替代已实现和已验证状态。
