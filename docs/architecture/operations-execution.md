# 持续运维执行设计

目标版本：0.3.0。状态：实现中的执行契约；验证结果另见 validation。
本设计沿用已确认的 Command/Adapter，产品范围由 [持续运维功能](../operations.md) 主管。

## 能力边界

| 能力 | 规则与计划 | 外部适配及受控副作用 |
| --- | --- | --- |
| 执行与互斥 | changes：版本化计划、有效期、身份与事实指纹、动作白名单 | Kubernetes API 集群锁、执行记录、逐步检查及取消 |
| 安全收尾 | security：原部署身份与保留管理身份、工具拥有的授权 | 主机备份、临时准备、新 SSH 通道验证、提交或自动回退 |
| 恢复 | recovery：制品/目标/版本约束与覆盖范围 | 只向全新隔离目录恢复配置和 etcd 数据，验证后发布结果 |
| 生命周期 | lifecycle：角色、PDB、仲裁、存储、版本与维护状态 | kubectl、kubeadm 与受限主机步骤；逐节点停止或恢复调度 |
| 诊断 | diagnostics：采集白名单、大小与敏感字段规则 | Kubernetes/主机只读采集，形成独立诊断制品 |
| 物料 | materials：版本、来源、平台、依赖与 SHA/digest | 准备包/镜像/Chart、校验、导入与企业仓库投递 |

CLI 只声明参数与选择能力，用例模块拥有确认、计划、执行与结果。不会引入任意命令 DSL，
配置、计划和远端请求均不能指定 shell/Python 正文。既有只读报告协议继续兼容。

## 计划与执行

可执行计划与只读建议区分，包含 schemaVersion、id、capability、clusterIdentity、目标、
createdAt/expiresAt、observationFingerprint 和已验证参数。计划 ID 是规范内容的 SHA-256；
计划持久化后仍视为不可信输入，每次读取重新验证协议、参数、ID 和时间。

执行要求对应计划 ID 的明确确认。取得集群锁后重新采集身份和能力相关事实，指纹不同则拒绝。
执行前持久化 running，每一步执行前检查锁所有权，完成后持久化 succeeded/failed/cancelled。
同一计划已成功时不重复执行；失败或中断留下明确步骤，不能通用盲重试。
不支持的拓扑/网段/存储变更直接拒绝；配置 apply 仅映射已实现的专属能力。

## 跨管理机锁

通过 API 中工具拥有的 ConfigMap 和 resourceVersion 条件更新竞争同一集群锁。
锁不会因超时或网络分区自动转移：长步骤可能仍在远端执行，自动过期会使第二个协调器并发变更。
普通退出在确认本次步骤结束后释放；协调器被 SIGKILL 时保留 owner、计划及步骤供诊断。
管理恢复须先确认旧协调器和远端任务均已停止，再以明确 owner 和当前 resourceVersion 解除。
主机变更同时持工具自己的主机 flock；不能删除正在使用的锁文件制造另一个锁 inode。

同一集群固定使用 kube-system，不能通过命名空间参数创建第二把互不相干的锁。
02 在现有 API 上使用同一 CAS 协议；首次部署在 API 就绪后取得锁。完成的 02 重跑只复核，
共享意图已变化则拒绝使用旧部署计划。原生阶段经独立 stage runner 持主机锁，子进程继承锁 FD。
05 的双节点 prepare/commit 跨 RPC 使用持久主机预留，并由同一主机锁保护；06/02 不得越过预留。
预留不自动过期；旧协调器和远端任务停止后才能在 05 选择回退或完成。它不等于跨节点数据库事务，
一端提交失败必须单独报告并按各节点实际内容恢复，不能忽略 finish 失败宣布完全完成。

锁是本工具协调器的互斥协议，不能阻止管理员或其他工具直接修改资源。因此每一步仍执行实际前提检查，
有差异就停止，不把锁当作 Kubernetes 全局事务。跨管理机测试必须包含竞争和进程崩溃，不能只用替身证明。

## 敏感数据与失败

主机请求通过已有可信 SSH 传送固定代码包和有限 JSON；代码来自当前完整工具包，不能由计划提供。
join 凭据只在临时私密通道处理，不进入计划、共享日志或命令行显示。私密备份采用受限目录；
常规报告只包含允许的事实与稳定错误类别。服务 reload 失败时回退原配置；控制面升级失败时停止，
不假设 kubeadm 支持自动降级，保留备份和恢复说明。

隔离恢复不覆盖现有数据目录，不以备份校验代替恢复。卷和应用数据库通过各自适配登记及检查，
不同保护范围的成功与缺失分别报告。

## 生命周期的继续与退出

失败/取消的旧计划保留为历史。继续操作重新采集事实、生成新 ID 和有效期，并再次确认；
只允许历史读取绕过旧计划过期检查，执行路径仍拒绝旧的过期计划。升级暂停调度时通过节点注解
记录维护计划，继续时仅接管已证明失败/取消的升级归属；管理员原先暂停的节点需要独立决策。
CoreDNS 计划只保存副本数和调度布局，不保存 Pod 环境、镜像凭据等字段；kubeadm 升级后恢复布局，
保留新镜像/模板迁移，并验证 updated/available 副本，不能只检查旧副本仍然 Ready。

worker 退出先检查 PDB、静态 Pod、节点本地 PV、Longhorn 副本与 CSI 挂载，再驱逐工作负载。
停止 kubelet 后只停止 API 已确认的 DaemonSet 沙箱，以 UID 条件删除 Node，最后发布清单。
保留磁盘、kubelet 身份与配置供检查，不自动格式化或 reset；旧主机重用前必须单独准备。
替换使用不同名称、地址和机器身份的已准备 worker，先退出旧节点，再以短期凭据加入新节点；
中间发布状态可诊断，失败后重新规划。此能力不自动修改控制面 etcd 成员。

PDB 规则按 Kubernetes eviction API 的实际语义处理 v1 空选择器、集合表达式、健康状态和过期预算，
最终驱逐仍由服务端裁决。实现依据为
[v1.36.5 eviction 源码](https://github.com/kubernetes/kubernetes/blob/v1.36.5/pkg/registry/core/pod/storage/eviction.go)。

## Cilium 补丁升级契约

首批组件生命周期只接受 Cilium 同 minor 的稳定补丁升级，目标 Chart 内容 SHA、版本、
原用户 values SHA、DaemonSet 和 operator Deployment 的 UID/更新策略进入计划。官方兼容性以 Cilium 1.20 文档的
Kubernetes 1.33–1.36 为边界；Helm 服务端预渲染另行验证 Chart 声明，不用声明代替上游支持表。

升级时暂用 OnDelete 冻结 agent/envoy 自动替换，operator 使用 maxUnavailable=0、maxSurge=1。
按节点顺序通过带 Pod UID 条件的 eviction 更新守护 Pod，遵守 PDB，每一项 Ready 后再继续。
最后核对每节点真实容器镜像、operator 实际 Pod、API/etcd/工作负载健康，并恢复计划捕获的原更新策略，再发布版本。
策略恢复使用同一目标 Chart 执行第二次受控 Helm 更新，同时恢复 Helm values 和 API 对象。
执行前在主机私密目录比较 Helm 保存清单与服务端渲染清单，只允许上述更新策略字段不同；
Pod 模板、ConfigMap、Secret 等有其他差异时拒绝，避免收尾产生额外滚动或重新生成证书。
不会通过两套独立 DaemonSet 各 maxUnavailable=1 就宣称全局一次只影响一个节点。

失败后保留锁、原策略与步骤；新的续跑计划沿用同一目标制品及稳定 rollout owner，仅处理未完成部分。
不把 Helm 原子回退当作 CRD/数据面的可逆事务；未知 pending Helm 状态需明确检查，不能通用强制删除历史。
values 和渲染结果始终留在 root 私密目录；普通计划只包含必要公开字段，不保存 Secret 或完整 values。

依据：[Cilium 官方兼容性](https://docs.cilium.io/en/stable/network/kubernetes/compatibility/)、
[1.20.4 Chart 配置](https://github.com/cilium/cilium/blob/v1.20.4/install/kubernetes/cilium/values.yaml)。
这是执行设计，不能当作此流程已经通过 E2E 的证明。

## 物料交付契约

物料准备、验证和导入属于独立 materials 模块；CLI 不执行配置中提供的任意下载命令。
首批离线目标固定为 Ubuntu 24.04 / linux amd64，明确基础系统要求。锁文件记录平台、
配置版本、软件包完整依赖闭包、镜像 manifest digest、Chart/工具版本、相对路径、大小及 SHA-256。
manifest ID 绑定规范内容；使用者须从可信交付渠道核对 ID，单独的自带哈希不构成来源认证。

构建器只从已配置的签名 APT 源解析完整依赖，镜像/Chart 使用明确版本与实际 digest；
所有制品校验后才能发布成功目录。离线导入使用自有根目录和独立签名的本地 APT 仓库，
安装阶段仅使用该仓库，禁止回退公共源或关闭 TLS 校验。01/02 及安装副本必须传递相同物料身份。
离线镜像先校验再导入 containerd，Cilium 与 Helm 使用包内 Chart/二进制；任何缺件在变更前拒绝。
企业仓库通过专属可信 HTTPS 配置适配，CA/认证引用与普通计划和报告分离；不接受 insecure_skip_verify。
实际断网首次安装、重跑、损坏制品和缺依赖需单独验证；准备包成功不能称为离线部署通过。

## 外部数据保护登记契约

etcd/配置备份不包含 PVC 内容和应用数据库。新增 protection 模块负责独立的保护对象登记，
不修改原备份的 coverage，也不将一个外部文件推断成“全量集群备份”。沿用 Command/Adapter：
公开描述文件绑定集群 UID、PVC 或应用工作负载 UID、创建时间、加密制品大小与 SHA；
age-archive 适配器只校验本机私密制品的格式和密文完整性，不执行用户提供的命令。
新适配器必须提供自己的有限输入、校验和恢复证据，不能借注册表执行任意 shell。

确认后把不含本机路径、密钥及制品正文的不可变记录写入自有 ConfigMap，使用既有集群 CAS 锁。
登记报告明确区分“用户声明对象”“密文完整性已校验”“解密未验证”“恢复未验证”；
后续对象重建、UID 不匹配或未登记 PVC 单独报告。任意数据库自动导出和生产原位恢复不由此动作执行。
制品实际可解密、目标数据完整和应用恢复可用仍需各自的隔离演练，不能由一次登记代替。

## Shell 模块约定

- 根入口保留版本查询、参数入口和用例编排；新增规则与具体操作放到对应 scripts 子模块。
- 共享 Shell 文件只定义有明确前缀的函数，不在 source 时安装软件或修改系统。
- 函数使用 local，命令参数用数组或独立参数传递；禁止 eval 和执行配置正文。
- 使用严格模式，同时显式检查关键命令状态，不能依赖复杂 if/管道中的 errexit 行为。
- 日志使用 messageKey；错误不打印可能含凭据的 BASH_COMMAND，工具原生输出与用户摘要分开。
- 候选配置先校验，再原子替换；变更前备份，trap 只负责当前操作拥有的临时资源。
- 源码包、节点安装副本及 systemd 续跑都必须包含同一组模块，不能只在仓库布局下可运行。

既有大入口按职责逐段抽取并保留行为回归，不为分文件而拆断状态所有权。测试检查真实函数和入口，
覆盖仓库布局、节点安装布局和错误/取消路径。
