## 定位与用户结果

沿用本项目“通过简单脚本选项完成复杂集群部署与维护”的定位，让管理员能够知道：
哪些生产对象受到监控、哪些风险未覆盖、故障或容量风险如何通知、收到通知后如何处理。
监控范围从业务访问结果向下覆盖入口、集群、数据与实际承载设施，而非仅确认 Pod Running。

需求来源为用户关于生产风险覆盖、可配置指标及企微/钉钉/飞书机器人和邮件通知的明确诉求。
未开展客户访谈或生产负载测量；不声明降低故障率、检测时间或成本的实测收益。

## 覆盖范围与启用原则

- 通用基线：节点/运行时、控制面/etcd、工作负载、DNS/网络、容量、监控自身及集群外可用性观察。
- 条件基线：登记为在用的 LB、Cilium、Longhorn/CSI、Gateway/Ingress、证书及虚拟化设施。
  对已登记的生产依赖，这些项目是必需覆盖项；因缺少采集能力不能降为“不适用”。
  0.4.0 对 Gateway/Ingress 与 CSI 驱动特定信号的支持缺口必须保留为未覆盖；入口管理与控制器适配归入 0.7.0。
- 备份调度、异地保护、校验及恢复结果的周期监控归入 0.5.0；0.4.0 覆盖报告必须显示这类在用备份风险尚未接线，不能把已有备份命令或一次性演练当成持续监控。
- 扩展：业务接口与流程、数据库/缓存/消息队列、GPU、对象存储、机房电力/温度及其他外部依赖。
  产品提供接入边界，不宣称替所有业务自动决定成功语义或接管外部设备。

允许选择少量关键对象先上线，但报告必须显示剩余缺口。风险清单是初版，
需随组件、事故和业务依赖变化维护，不宣称穷尽所有故障。

## 告警语义

采集指标用于观察、诊断和趋势分析；通知必须对应可解释的业务影响或需要处理的风险。
每条通知应包含稳定风险 ID、事件关联 ID、集群/对象、状态、时间、观测值、判断依据、
接收责任组、看板链接及处置手册引用。文本使用 messageKey 与 en/zh_CN/zh_TW 目录；
指标名、风险 ID 和第三方响应不随语言改名。

| 类型 | 目的 | 示例 |
| --- | --- | --- |
| 故障告警 | 提示已发生的服务或数据处理异常 | 关键入口不可用、etcd 无仲裁、关键服务无可用副本 |
| 风险预警 | 在冗余或容量继续恶化前安排处理 | 卷副本不足、证书将到期、磁盘预计耗尽、失去一个故障域后的承载不足 |
| 趋势与诊断 | 为定位和规划提供证据，通常不立即通知 | 资源增长、历史重启、时延分布和单次可恢复事件 |

建议分级为 P0（关键业务中断/明确严重数据风险）、P1（明显降级或关键冗余丢失）、
P2（有处置时间的风险）、INFO（记录与规划）。这是本项目拟议语义，不套用厂商级别；
实际等级由服务重要性、影响范围与维护状态决定。单节点故障不一律 P0，CPU 高不直接等于服务中断。

分组、抑制与静默只控制通知，不删除原始故障记录；维护有对象、责任人、原因和到期时间。
故障恢复需要独立判定，数据消失、采集权限丢失或心跳停止不能作为恢复。
SLO 告警考虑长短窗口的错误预算消耗；不能依靠很长的持续时间掩盖完全不可用。

## 规则、配置与数据契约目标

覆盖矩阵是风险级定义，不是可直接执行的 PromQL。实现前，每个启用项应形成以下规则记录：

| 字段组 | 必须明确的内容 |
| --- | --- |
| 身份与适用性 | 风险/规则 ID、规则修订、所属功能、集群/环境、对象和预期标签、适用组件/版本 |
| 指标语义 | 实际指标名、类型、单位、分母、聚合维度、来源端点、认证引用、采集与新鲜度窗口 |
| 判断与恢复 | 表达式、阈值/趋势、观察与持续窗口、最小样本/流量、缺失处理、恢复条件/滞回 |
| 影响与处置 | 等级、责任组、影响说明、处置手册、看板和关联抑制条件 |
| 通知与验证 | 渠道引用、分组/重复周期、故障/恢复通知、验收用例、最后验证证据 |

不复制云厂商 PromQL 后直接启用。需核对当前版本的标签、指标类型和单位；
OOM 必须关联原因而非仅数重启，Ready=False 与 Unknown 均需考虑，低流量下不盲算错误率。
历史样本不足时趋势预测标为未核验。业务 ID、URL 查询参数、用户标识等不得无限进入指标标签。

环境配置需明确关键业务、责任组、SLO/探测成功条件、通知检测预算、容量安全余量、
备份新鲜度/RPO/RTO、保留期及监控资源预算。这些值尚未实测或批准，不在本轮编造统一生产默认值。
缺少必需参数时给出未完成项，不能用静默关闭告警获得“生产就绪”。

## 通知和集群外观察的边界

目标接入邮件及企微、钉钉、飞书群机器人，允许一条规则关联多个渠道和责任组。
SMTP 与机器人使用不同协议；群机器人和企业应用消息接口不得混为一种配置。
通知服务实现及开源方案选型尚未锁定，不在目标文档中冒称已有适配器。

渠道须支持协议校验、模板、故障/恢复、超时、平台业务失败、限流和有上限的重试，
记录尝试与送达状态。超时后平台可能已收到消息，应允许“结果未知”，不能承诺跨平台严格一次送达。
持久化重试、重启恢复、重复控制和多实例行为必须在设计与验收中明确。
平台成功应答不等于人员已阅读；人员确认/值班升级是独立能力，尚未定义自动接管。

Webhook、签名密钥、SMTP 密码和探测凭据通过受限 Secret/凭据引用管理，
不写入公开配置、命令行日志、普通报告或备份元数据。真实发送仅在明确授权的测试渠道进行。
机器人需要相应出站网络，离线集群必须登记邮件中继/代理或外部通知服务，不能承诺纯离线直达公网。

外部观察必须有自己的调度、检测与通知路径，不能仅在集群内运行 Blackbox Exporter，
也不能把外部探测结果只交给已宕机的集群内 Alertmanager。
登记宿主机、机架/电源、存储和网络依赖，显示共同故障域；不把增加一台同宿主 VM 视为异地容灾。

## 目标达成的判定

1. 每个必需风险都有适用判定、有效配置、数据和规则核验、负责人及对应验收证据；
   未覆盖项显式阻止该配置被标为“监控基线验收通过”。可部分上线，但不能隐藏盲区。
2. 每个宣称支持的通知渠道均有授权测试渠道的故障与恢复送达证据，缺少真实渠道记为未验收。
3. 外部观察在集群内监控不可用时仍能独立通知；通知服务自身失败也有可观察结果。
4. 必需风险的检测与通知时延落在环境预先批准的预算内；未设置预算只能报告实测，不能判 SLA 达成。
5. 保存重复通知、漏报、采集缺失、检测/送达时延、容量与恢复演练的数据，支持后续调整。
   无数据时不声称精确率或“零漏报”。覆盖比例须列出分母、排除原因，不能用高比例掩盖关键缺口。
